# Архитектура HandDraw ESP

## 1. Разделение ответственности

Проект сознательно не реализует генератор шаговых импульсов заново.

**FluidNC на ESP32** отвечает за жёсткое реальное время:

- планирование ускорений;
- STEP/DIR для X и Y;
- homing и программные границы;
- управление RC-сервоприводом как осью Z;
- чтение G-code из SD/flash;
- аварийные и realtime-команды;
- HTTP, WebDAV и WebSocket.

**HandDraw WebUI**, также размещённая на ESP32, отвечает за подготовку задания:

- текст и штриховые шрифты;
- SVG и растровые изображения;
- преобразование в полилинии;
- размещение на листе;
- оптимизацию порядка;
- предпросмотр;
- генерацию G-code;
- загрузку и наблюдение.

Браузер выполняет тяжёлую геометрию. ESP32 получает уже готовый G-code, поэтому память контроллера не расходуется на разбор фотографий и сложных SVG.

## 2. Единая модель траектории

После любого источника данные имеют один формат:

```js
[
  [ {x: 10.0, y: 12.0}, {x: 20.0, y: 15.0}, ... ],
  [ {x: 48.0, y: 22.0}, {x: 48.0, y: 36.0}, ... ]
]
```

Координаты задаются в миллиметрах, начало страницы находится сверху слева. Каждый вложенный массив — непрерывный штрих с опущенным пером. Переход между массивами выполняется с поднятым пером.

Эта модель используется одновременно для:

- SVG-предпросмотра;
- расчёта габаритов;
- оценки времени;
- оптимизации холостого хода;
- экспорта SVG;
- генерации G-code.

Поэтому предпросмотр не является декоративной картинкой: геометрия совпадает с заданием станка.

## 3. Текст и шрифт

Шрифт хранит открытые штрихи, а не залитые контуры. Для каждого символа задаются:

- ширина продвижения;
- один или несколько вариантов начертания;
- один или несколько штрихов;
- нормированные координаты в em-квадрате.

При раскладке применяются размер, коэффициент ширины, наклон, интервалы, выравнивание и воспроизводимая случайная вариативность. Если строчной кириллической буквы нет, ядро ищет соответствующую прописную и рисует её в настраиваемом масштабе 35–100%. Это даёт малые прописные без удвоения JSON; собственный шрифт может содержать отдельный нижний регистр.

## 4. SVG

`web/src/svg-import.js` использует геометрический движок браузера:

1. SVG разбирается в скрытом контейнере.
2. Для видимых `path`, `line`, `polyline`, `polygon`, `rect`, `circle` и `ellipse` получается итоговая матрица преобразования.
3. Длина элемента измеряется стандартным SVG API.
4. Элемент равномерно сэмплируется через `getPointAtLength()`.
5. Точки проходят упрощение Рамера—Дугласа—Пекера.
6. Результат вписывается в выбранную страницу.

Так поддерживаются линейные и криволинейные сегменты, включая дуги, без собственного неполного парсера команд SVG.

## 5. Растр

Доступны два режима.

### Штриховка

Пиксели переводятся в относительную темноту. На каждой строке формируются непрерывные участки, где темнота превышает порог. Плотность задаётся шагом строк. Результат хорошо подходит для фотографий, теней и фактур.

### Контуры

Из порогового бинарного поля выделяются границы тёмных областей. Соседние сегменты объединяются в линии, затем упрощаются. Режим предназначен для логотипов, пиктограмм и контрастных рисунков.

## 6. Оптимизация

Оптимизатор выбирает ближайший следующий штрих. При разрешённом развороте сравниваются оба конца линии. Это эвристика ближайшего соседа: она не гарантирует глобальный минимум, но быстро уменьшает холостой ход для сотен и тысяч штрихов прямо на телефоне.

Оптимизация не меняет геометрию штрихов, только их порядок и иногда направление.

## 7. G-code

Генератор выдаёт метрический абсолютный код:

```gcode
G21
G90
G0 Z5
G0 X10 Y287 F4000
G0 Z0
G4 P0.12
G1 X30 Y287 F1200
G0 Z5
```

Координата страницы Y инвертируется при переводе в систему станка. Для каждого штриха сохраняется диапазон байтов в итоговом файле. Процент FluidNC сопоставляется с этими диапазонами, поэтому WebUI подсвечивает завершённые и текущие штрихи.

Перед запуском проверяются:

- конечность всех координат;
- наличие минимум двух точек в линии;
- выход за габариты страницы;
- положительные скорости;
- безопасные положения пера;
- имя файла.

## 8. Обмен с ESP32

| Операция | Интерфейс FluidNC |
|---|---|
| Проверка контроллера | `/command?commandText=[ESP800]` |
| Команды G-code | WebSocket с протоколом `arduino`; `/command` как резерв |
| Realtime `? ! ~ Ctrl-X` | WebSocket; запрос состояния каждые 500 мс |
| Запись на SD | multipart `/files` в HTTP-путь `/sd/jobs/...`; WebDAV как резерв |
| Запись во flash | WebDAV `PUT /flash/file.gcode` |
| Запуск SD | `$SD/Run=/jobs/file.gcode` |
| Статус | `<Run|MPos:...|SD:37.25,/jobs/file.gcode>` |

HTTP и WebSocket работают с того же origin, когда страница открыта с ESP32. Это основной и рекомендуемый режим.

До подключения станка интерфейс умеет проиграть ускоренную локальную симуляцию. Она использует те же полилинии и диапазоны байтов, что и реальное задание, поэтому показывает фактический порядок штрихов, а не отдельную декоративную анимацию.

## 9. Автономная сборка WebUI

`scripts/build_webui.py`:

1. читает HTML, CSS и ES-модули;
2. устраняет только известные импорты/экспорты;
3. встраивает технический шрифт JSON;
4. встраивает CSS и JavaScript;
5. проверяет отсутствие runtime-зависимостей;
6. создаёт `dist/index.html`;
7. создаёт детерминированный `dist/index.html.gz`;
8. сохраняет SHA-256 в `dist/manifest.json`.

Загрузка одной сжатой страницы делает обновление атомарным и снижает число файлов во flash.
